## 1. 의도와 이유

운영 중인 서비스에는 현업, 실사용자, QA로부터 결함 제보, 불편사항, 개선 요청, 신규 기능 제안이 계속 들어온다. 이 요청이 PM과 개발자에게 그대로 몰리면서 업무 병목이 생긴다.

MyProjectManager는 요청이 개발자에게 닿기 전에 **역할별 AI 에이전트가 1차로 검토하고 응답**해서 다음 두 가지를 달성하는 도구다.

1. 이미 처리 중이거나(중복), 이미 해결됐거나, 정상 동작인 요청은 AI가 근거와 함께 알려주고, **요청자가 스스로 판단해** 제출하지 않거나 기존 티켓에 합류하게 해서 **티켓 총량을 줄인다.**
2. 남은 티켓은 인터뷰로 정보를 보강하고 담당 대상을 추천해서 **개발자가 바로 일할 수 있는 상태로 넘긴다.**

이 프로젝트는 형준의 이전 프로젝트 CRDD(레포를 분석해 사람이 읽을 문서를 만드는 도구)의 확장판이다. CRDD를 실제로 운영해 보니 코드 단위의 세밀한 분석은 큰 도움이 되지 않았다. 그래서 이번에는 **레포를 개요 수준으로만 이해**하고, 판단의 근거를 도메인 지식과 티켓 이력에 둔다. [결정]

### 왜 만드는가 [결정]
- **포트폴리오용 사이드 프로젝트.** 수익화가 목적이 아니다.
- **주된 목표**: AI 에이전트 설계 역량을 보여주는 것. 보여주는 방법은 6.13절.
- **부차 목표**: 개발팀의 협업 방식(티켓 생애주기, 배정, 이관, 종결)을 이해하고 있다는 것을 보여주는 것.
- **가정하는 타깃 사용자**: 프로젝트를 관리하는 PM급 개발자, 시스템 담당자.
- **실제 사용자**: 당분간 형준 혼자. 실제 개발팀원에게 테스트를 부탁할 예정이다.

## 2. 역할

| 역할 | 하는 일 |
|---|---|
| 요청자 (현업, 실사용자, QA) | 티켓 작성(긴급도와 담당 대상 지정). 바로 제출하거나 AI 검토를 요청. AI 응답을 보고 철회, 기존 티켓 합류, 계속 진행, 제출을 스스로 고름. 처리 완료된 티켓을 확인해 종결하거나 재오픈. 언제든 자기 티켓을 회수(종결) |
| 리드 (PM 역할을 겸하는 개발자, 관리자) | 대상이 없는 티켓(리드 큐)의 대상 지정. **"안 하기로 함" 종결은 리드만.** 도메인 지식, 에이전트 지시사항, 프로젝트·멤버·그룹 관리. 리드 자신도 개발자로 배정받을 수 있음 |
| 개발자 | 자기에게 온 티켓과 자기 그룹 큐의 티켓을 가져가 처리(수락, 보류, 처리 완료). 내 일이 아니면 사유와 함께 이관. 종결도 할 수 있으나 "안 하기로 함"은 제안만 가능 |

- PM과 개발자는 별개 직군으로 나누지 않는다. 리드 개발자가 PM 역할을 겸하는 작은 팀이나 SI 현장을 가정한다. [결정]
- 역할 이름(요청자 / 리드 / 개발자)과 권한 구분은 [제안]이다.

## 3. 목표, 비목표, 반목표

### 목표
- 요청자 흐름부터 AI 검토, 배정, 개발자 처리, 요청자 확인과 종결까지 **티켓 한 건의 생애주기 전체를 자체 웹 화면에서 완결**한다.
- AI가 한 일과 사람이 한 일의 경계가 명확하고, AI의 모든 판단에 **근거가 기록**된다. [제안]
- 관리자가 **배포 없이** 도메인 지식과 에이전트 지시사항을 바꿀 수 있다. [결정]
- **"AI 응답을 보고 요청자가 제출하지 않았거나 기존 티켓에 합류한 수"를 측정**할 수 있다. [결정: 티켓 총량 감소가 목적 / 제안: 집계 방식]

### 3.1 AI 활용 원칙: 보수적으로, 결정은 사람이 [결정]
빠르지만 틀린 처리 한 건보다, 조금 느려도 정확한 처리가 낫다. 최종 결정과 책임은 티켓을 요청한 사람과 처리하는 사람에게 있다.
- **AI는 제안만 한다.** 배정 대상, 긴급도, 종결, 철회는 모두 사람이 누른다. AI가 값을 직접 바꾸는 동작은 없다.
- **근거 없으면 제안하지 않는다.** 중복·이미 해결됨·정상 동작 제안은 실제 티켓 링크, 커밋/PR, 도메인 지식 항목 같은 근거가 있을 때만 띄운다. 근거는 항상 함께 보여준다. [Claude 결정]
- **모르면 넘어간다.** 판단이 어려우면 제안 없이 다음 단계로 가는 것을 정상 동작으로 본다. 억지로 고르지 않는다. [Claude 결정]

### 비목표 (1차) [제안]
- Slack, Jira 연동. 장기적으로는 연동을 거쳐 대체하는 것이 목표지만[결정], 4차로 미룬다.
- 코드 단위의 세밀한 분석(함수나 라인 단위 원인 추정). [결정]
- AI가 우선순위를 정하거나 조정하는 기능. 우선순위는 요청자·리드·개발자가 판단한다. [결정]
- 부하 계산에 기반한 자동 배정. [결정, 12절]
- 칸반 보드 꾸미기, 알림 세부 설정 등 포트폴리오 가치가 낮은 기능. 최소한으로만 둔다.
- 결제, 멀티테넌시 과금 등 상용화 기능.

### 반목표 (동작하더라도 이러면 실패)
- **AI가 티켓 제출을 막는 것.** AI는 안내만 하고 제출 여부는 항상 요청자가 정한다. [결정]
- **AI가 근거 없이 해소를 제안하는 것.** 잘못된 제안으로 실제 결함이 철회되면 개발팀은 영영 모르게 된다. [결정, 3.1]
- AI가 사람의 결정(대상, 긴급도, 상태)을 대신 바꾸는 것. [결정, 3.1]
- 같은 티켓을 넣었을 때 처리 경로가 매번 달라서 판단을 추적할 수 없는 것. 이것이 하이브리드 구조를 선택한 이유다.

## 4. 제약
- 개발자는 형준 1인. 개발은 2026-11-24 주간부터 시작한다.
- 기술 스택은 4.1절에 따른다. [결정, 2026-11-24 기술 스택 논의]
- 시연 대상 서비스는 교체할 수 있어야 한다. 처음부터 **여러 프로젝트를 등록**할 수 있는 구조로 만든다. [결정: 교체 가능 / 제안: 다중 등록 구조]
- 보안 때문에 소스코드 유출을 꺼리는 고객을 고려한다. 지금은 기능을 만들지 않고 **갈아끼울 지점만 분리**한다(4.2절, 10.4절). [결정]
- 개발 의욕을 유지할 수 있게 **작은 단계(1차~4차)로 나눠** 단계마다 동작하는 결과를 낸다(7절). [결정]

## 4.2 갈아끼울 지점 (보안 모드 대비) [결정: C안]
지금은 기능을 만들지 않되, 다음 세 곳은 인터페이스로 분리해 나중에 구현만 추가할 수 있게 한다.
- **레포 정보 출처**: GitHub API(1차) / 로컬 스캔 CLI(4차). 분석기는 출처와 무관한 같은 형식의 레포 정보를 받는다.
- **AI 모델**: 클라우드 제공자 / 로컬 모델. 4.1의 제공자 레지스트리로 이미 분리됨.
- **Vercel 전용 기능**: 첨부파일 저장소는 감싸서 S3 호환 저장소로 교체 가능하게 하고, 작업 큐와 주기 실행은 특정 플랫폼 기능에 기대지 않는다(주기 실행은 HTTP 엔드포인트 하나로 두어 어떤 스케줄러로도 호출 가능).

## 4.3 디자인 방향 [결정]
- 시안 3개(A 구조형 / B 문서형 / C 개발자형) 중 **A 구조형**을 택했다. 목록 | 본문·활동 | 속성·처리 버튼의 3단 구조.
- 첫인상: 가시성·가독성 우선, 깔끔함, 깔끔한 동적 애니메이션. 여백은 넉넉하게. 라이트·다크 모두 지원.
- **강조색은 프로젝트의 AI 제공자를 따른다**(Claude 어두운 오렌지, ChatGPT 옥색, Gemini 파랑 등). 사용자는 강조색을 바꿀 수 있다.
- AI가 한 일은 판단을 만든 제공자의 색으로 표시하되, 강조색과 겹칠 수 있으므로 아이콘·제공자 이름·연한 바탕으로 구분한다.
- 글꼴은 개발자 친화적으로: JetBrains Mono(번호·시각·코드) + 한글 본문용 IBM Plex Sans KR.
- 세부 규칙은 `docs/design/design-rules.md`에 둔다. 이후 화면 작업은 이 규칙을 따른다.
- 흐름 도식은 `docs/design/diagrams/`에 둔다(1~5장).

## 5. 접근 방식

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| A. 고정 파이프라인 | 단계를 코드로 고정하고, 단계마다 LLM을 한 번 호출해 구조화된 결과를 받음 | 예측 가능, 테스트 쉬움, 저렴 | AI가 폼 처리기처럼 보여 에이전트 설계 역량을 보여주기 약함 |
| B. 오케스트레이터 + 하위 에이전트 | 총괄 에이전트가 어떤 역할 에이전트를 부를지 스스로 결정 | 유연하고 화려함 | 경로가 매번 달라 근거 추적이 어려움. 비용과 디버깅 부담이 큼. AI와 사람의 경계 목표와 충돌 |
| **C. 하이브리드 (선택)** | 바깥 단계는 코드로 고정하고, 각 단계 안에서만 역할 에이전트가 정해진 도구를 골라 씀(호출 상한 있음) | 단계 경계와 책임이 명확해 추적 가능. 단계 안에서는 실제 에이전트처럼 동작. 관리자가 역할 프로필을 바꾸는 요구와 잘 맞음 | A보다 구현량이 많음 |

**C를 선택했다.** [결정] 에이전트 설계 역량은 "단계 안에서 도구를 골라 쓰는 역할 에이전트"로 보여주고, 협업 이해도는 "고정된 티켓 생애주기"로 보여준다.

## 6. 결정된 설계

### 6.1 프로젝트 등록과 레포 이해
- 관리자가 프로젝트를 등록한다. 입력 항목은 원격 저장소 URL(1차는 GitHub), 도메인 지식, 비즈니스 규칙이다. [결정]
- 레포 분석은 **개요 수준만** 한다. [결정] 다음 항목을 뽑아 저장한다. [제안]
  - 기술 스택, 디렉터리와 모듈 구조
  - 도메인 맵: 업무 도메인(요약, 메모, 카테고리 등)과 그 도메인을 담당하는 모듈. 모듈·화면·API마다 그룹 태그(6.6)를 제안한다
  - 화면 목록, API 목록(이름 수준)
  - 최근 커밋과 PR 목록. "XX일 전에 조치됨" 판단의 근거로 쓴다
- 분석 결과는 관리자가 확인하고 수정할 수 있다. [제안]
- 분석 결과는 관리자 화면이 아니라 **별도 진입점**(상단 바의 "레포" 메뉴)에서 본다. 모든 멤버가 볼 수 있고, 그룹 태그 수정과 다시 분석은 리드만 한다. [결정: 별도 진입점 / Claude 결정: 권한]
- 등록한 서비스의 **기능 설명 가이드 화면**은 3차로 미룬다(10.5). 그때 이 진입점을 "가이드"로 넓히고, 레포 개요는 그 안의 개발자용 탭이 된다. [결정: 미룸]
- 재분석 시점(수동 버튼, 주기적 실행 등)은 [빌더 재량]이다. 단, 수동 재분석은 반드시 있어야 한다.
- [Claude 결정] 레포 접근은 **GitHub API만** 쓰고 클론하지 않는다. 1차는 공개 레포를 기준으로 하고, 비공개 레포는 프로젝트별 읽기 전용 토큰을 선택 입력으로 받는다(암호화 저장).
- [Claude 결정] **"이미 해결됨"의 근거 우선순위**는 다음과 같다.
  1. 이 시스템 안에서 종결(해결 확인)된 티켓(가장 강한 근거)
  2. 종결 티켓에 연결된 PR/커밋(개발자가 처리 완료할 때 선택적으로 링크)
  3. 커밋과 PR 메시지 텍스트(약한 근거). 이것만 있으면 단정하지 않고 "관련 변경이 있었던 것으로 보인다"로 표현하고, 그 변경을 함께 보여준다.

### 6.2 도메인 지식과 에이전트 역할 관리 [결정]
- 도메인 지식, 비즈니스 규칙, 에이전트별 역할과 지시사항을 **서비스 안의 관리자 화면에서 수정**하고 즉시 반영한다.
- [제안] 지시사항은 수정할 때마다 버전으로 저장한다. 각 AI 판단 기록에는 사용한 지시사항 버전을 남긴다. "왜 지난주와 판단이 달라졌는가"를 추적하기 위해서다.
- [제안] 역할 프로필 구성: 이름, 지시사항, 사용 가능한 도구 목록, 모델, 도구 호출 상한.

### 6.3 요청자 흐름 [결정]
1. 문제, 개선점, 신규 기능 제안이 생긴다.
2. 프로젝트를 고르고, 카테고리(결함, 개선사항, 신규 기능 등)와 **긴급도**를 선택하고, 내용을 작성한다. 첨부파일을 올릴 수 있다. **담당 대상**(사람 또는 그룹, 6.6)을 지정할 수 있다(선택).
3. **바로 제출** 또는 **검토 요청**을 누른다. 요청자가 스스로 판단한다. 바로 제출하는 요청자가 많은 것은 Jira와 같은 현실로 받아들인다. [결정]
4. 검토를 요청하면 AI가 **먼저 중복을 확인**한다. 비슷한 티켓이 있으면 링크와 함께 보여주고 요청자가 고른다. [결정]
   - **같은 건이에요**: 작성 중인 티켓은 폐기하고, 작성한 내용은 기존 티켓에 **댓글로 붙는다.** 요청자는 기존 티켓의 구독자가 되어 진행 알림을 받는다.
   - **다른 건이에요**: 그대로 다음 단계로 간다. AI 판단과 달리 요청자가 아니라고 하면 중복이 아닐 수 있다.
5. 이어서 AI가 해소 가능성을 확인한다. 근거가 있을 때만(3.1) 다음 응답을 보여준다.
   - **이미 해결됨**: XX일 전에 조치되어 해결되었다.
   - **정상 동작**: 업무 프로세스상 정상적인 처리 결과로 보인다.
   요청자는 **"해결됐어요(철회)" / "인터뷰 계속" / "그대로 제출"** 중에서 고른다. 자동 철회는 없다. [결정]
6. 해소되지 않으면 AI 인터뷰로 정보를 보강한다(인터뷰 설계 문서).
7. 제출할 때 AI가 **담당 대상을 추천**해 근거와 함께 미리 채운다. 요청자는 확인하거나 바꾼다. [제안, 6.6]
- **기다리지 않아도 된다.** [결정] 검토를 요청한 뒤 화면을 떠나도 되고, 다음 단계(중복 후보, 해소 응답, 질문)가 준비되면 앱 안 알림이 간다. 티켓 화면에는 지금 어느 단계인지("중복 확인 중 → 질문 준비 중 → 답변 대기")가 보인다. 1차는 짧은 주기 새로고침(폴링)이나 SSE로 갱신하고, 진짜 실시간은 3차에 붙인다. [Claude 결정: 1차 갱신 방식]
- [제안] **바로 제출한 티켓도** 백그라운드에서 중복·해소 분석을 돌린다. 요청자에게 말을 걸지는 않고, 결과를 비고와 중복 후보 표시로만 남긴다. 담당자가 보고 판단한다.

### 6.4 비고 기록 [결정]
- 요청이 터무니없거나 이미 반영된 항목이면 AI는 요청자에게 안내만 하고 제출은 막지 않는다. 그 판단 이력은 티켓의 비고 항목에 남긴다.
- [제안] 비고에는 판단 유형, 근거(참조한 티켓 ID, 커밋, 도메인 지식 항목), 지시사항 버전을 구조화된 형태로 남긴다.

### 6.5 긴급도 [결정, 12절에서 변경]
- **요청자가 등록할 때 정한 긴급도로 고정한다.** AI는 긴급도를 바꾸지 않는다.
- AI는 정리본에 **참고 문구**만 남긴다(예: "비슷한 티켓은 주로 '보통'이었어요"). 이 문구가 리소스나 처리 시간을 늘리면 빼도 된다. [결정]
- [Claude 결정] 사람(요청자, 리드)이 긴급도를 바꿀 수는 있고, 바꾸면 이전 값·새 값·바꾼 사람이 이력에 남는다.
- 긴급도 단계 수와 이름은 [빌더 재량]이다. 기본 3~4단계를 권장한다. 도식의 긴급도 표시(높이가 다른 막대 4개)는 디자인 규칙을 따른다.

### 6.6 배정: 뷔페 방식 [결정, 12절에서 변경]
- **담당 대상은 사람 또는 그룹**이다(예: ITS팀, 외주개발사, 김형준 개발자). 요청자가 티켓을 만들 때 지정한다. [결정]
- **AI는 추천만 한다.** 검토를 요청한 티켓은 제출 직전에 AI가 추천 대상과 근거를 미리 채우고, 요청자가 확인하거나 바꾼다. 바로 제출한 티켓은 요청자가 고른 대상 그대로 간다. [제안]
- 대상에 따라 다음 큐로 간다. [제안]
  - **사람**: 그 사람에게 배정된다(배정됨). 그 사람이 수락하면 진행중.
  - **그룹**: 그룹 큐에 올라가고, 그룹원 누구나 **가져간다**("뷔페"). 가져가면 진행중.
  - **비어 있음**: **리드 큐**에 올라간다. 리드가 대상을 지정하거나 직접 가져간다. 백그라운드 분석의 AI 추천이 참고로 보인다.
- **이관** [결정]: 받은 사람이 내 일이 아니면 사유와 함께 다른 사람, 그룹, 또는 리드 큐로 넘긴다. 이관은 이력에 남고, 받는 쪽에 알림이 간다. (기존의 "반려"는 이관으로 대체한다.)
- [Claude 결정] **그룹 목록은 하나만 둔다.** 관리자가 프로젝트마다 그룹과 그룹원을 정한다. 한 사람이 여러 그룹에 속할 수 있다. 그룹에는 담당 범위 설명과, 선택적으로 레포 개요의 모듈·화면·API 태그를 붙일 수 있다(AI 추천과 분야 에이전트의 자료 범위에 쓰인다). 이전 설계의 "영역"은 이 "그룹"으로 통합한다.
- 부하 계산 기반 자동 배정과 확신도 기준값은 **두지 않는다.** [결정]
- 추천 적중률은 "AI 추천 대상과 종결 시점 담당 대상이 같은가"로 측정한다(8절).

### 6.7 개발자 처리와 종결 [결정]
- 개발자는 자기에게 온 티켓을 **수락**하거나 그룹 큐에서 **가져가서** 진행한다. 진행 중에 **보류**(사유 필수, 같은 담당자가 재개)할 수 있다.
- 다 고치면 **처리 완료**를 누른다. 티켓은 **확인 대기**가 되고 요청자에게 알림이 간다. 선택적으로 PR/커밋을 링크한다.
- 요청자는 확인 대기 티켓에서 **"고쳐졌어요"**(종결, 사유: 해결 확인) 또는 **"아직이에요"**(재오픈, 사유 입력 → 진행중)를 누른다.
- **확인 대기는 자동 종결하지 않는다.** 요청자가 확인하지 않으면 계속 남는다. 요청자가 보낸 티켓이니 확인하지 않는 손해는 요청자 몫이다. [결정]
- **종결**은 모든 티켓의 최종 상태다. 종결에는 사유를 고르거나 입력한다. [결정]

| 종결 사유 | 누가 | 비고 |
|---|---|---|
| 해결 확인 | 요청자(기본), 리드, 담당 개발자 | 보통은 요청자나 리드가 한다 |
| 안 하기로 함 | **리드만** [결정] | 개발자는 "안 하기로 함 제안"까지만(리드에게 알림). 요청자에게 사유가 보인다 |
| 중복 | 리드, 담당 개발자 | 원본 티켓 링크 필수. 요청자는 원본 구독자가 된다 |
| 요청자 회수 | 요청자 | 언제든 가능(예: 내 실수였음). 사유 선택 또는 입력, 담당자에게 알림 |
| 기타 | 리드 | 직접 입력 |

- [Claude 결정] 종결된 티켓도 열람과 댓글은 가능하다. 다시 열려면 리드가 재오픈한다.

### 6.7.1 티켓 상세 화면과 댓글 [결정]
- 티켓 상세 화면에는 **AI 인터뷰(검토 요청과 AI 응답 왕복) 내역 전체**, AI 판단 비고, 긴급도와 담당 대상 변경·이관 이력, 상태 변경 이력이 모두 보인다.
- 요청자와 개발자는 티켓에 **댓글 형식으로 대화**할 수 있다. 실시간일 필요는 없다.
- 댓글이 달리면 상대(요청자, 담당자, 구독자)에게 **알림**이 간다.
- [Claude 결정] 댓글 기능과 위의 이력 표시는 **1차에 포함**한다. 알림은 1차에서 **앱 안의 알림 목록**(폴링으로 갱신)으로 두고, 실시간 푸시는 3차에 붙인다. 댓글과 알림도 10.2의 이벤트로 기록한다.

### 6.8 티켓 상태 [제안, 12절에서 변경]
```
작성중 ─(검토 요청)→ AI검토중 ⇄ 요청자확인대기 ─┬─(해결됐어요 / 같은 건이에요)→ 철회(AI해소)
   │                                            └─(제출)──┐
   └──────────────(바로 제출)─────────────────────────────┤
                                                          ▼
                           대상이 사람 → 배정됨 / 그룹·없음 → 큐 대기(그룹 큐 / 리드 큐)
배정됨 ─(수락)→ 진행중,   큐 대기 ─(가져가기 / 리드가 대상 지정)→ 진행중 / 배정됨
진행중 ⇄ 보류,   배정됨·큐 대기·진행중 ─(이관)→ 배정됨 / 큐 대기
진행중 ─(처리 완료)→ 확인대기 ─(고쳐졌어요)→ 종결
                     └─(아직이에요, 재오픈)→ 진행중
(제출 이후 어느 상태든) ─(종결: 사유 선택)→ 종결
```
- 상태값(제안): `draft`, `ai_reviewing`, `awaiting_requester`, `withdrawn_ai_resolved`, `queued`, `assigned`, `in_progress`, `on_hold`, `resolved`(확인 대기), `closed`(종결, `closeReason` 필수).
- "철회(AI해소)"는 반드시 따로 집계할 수 있어야 하고, 유형(중복 합류 / 이미 해결됨 / 정상 동작)을 남긴다.
- 세부 이름과 전이 구현은 [빌더 재량]이다.

### 6.9 에이전트 단계 (하이브리드 구조) [제안]
바깥 단계와 각 단계의 역할 에이전트는 인터뷰 설계 문서(`2026-11-24-ticket-interview-design.md`)를 따른다. 요약하면 다음과 같다.

| 단계 | 역할 에이전트 | 출력 |
|---|---|---|
| ① 중복 확인 | 해소 검사 | 중복 후보 티켓과 근거(없으면 없음) |
| ② 해소 확인 | 해소 검사 | 이미 해결됨 / 정상 동작 제안과 근거(근거 없으면 제안 없음) |
| ③ 인터뷰 | 리드 에이전트(1차 혼자, 2차부터 분야 에이전트와 함께) | 선택형 질문 |
| ④ 정리 | 정리자 | 정리본(긴급도 참고 문구 포함) |
| ⑤ 대상 추천 | 분류 | 추천 대상(사람/그룹), 근거. 모르면 추천 없음 |

- 모든 출력은 정해진 스키마로 받는다. 모든 호출은 `ai_judgments`에 남는다.
- 바로 제출한 티켓은 ①②④⑤를 "요청자에게 응답하지 않는 모드"로 실행한다.
- 첨부 문서(PDF, PPT 등)를 읽고 요약하는 부분은 **분리된 모듈**로 둔다. 친구의 문서 요약 요청과 병합할 가능성에 대비하기 위해서다(11절 참고).
- 에이전트 실행은 요청 처리 흐름과 분리해 백그라운드 작업으로 돌린다. 큐 구현 방식은 [빌더 재량]이다.

### 6.10 시연 구성 [결정, 12절에서 변경]
- 시연 대상 레포는 **MyProjectManager-sample-repo**다. Workwrap(github.com/PorkbellyCode/workwrap) 소스를 복제하고 **의도적으로 결함을 심은** 임시 레포다. 이후 더 큰 프로젝트로 교체하거나 추가한다. [결정]
- 이 레포는 시연 대상이면서 동시에 **정답이 있는 시험지**다. 다음을 함께 준비한다. [제안]
  - **정답표**: 심은 결함마다 위치, 그룹, 증상, 개발자에게 필요한 정보, 기대하는 AI 응답.
  - **커밋 이력**: 일부 결함은 커밋으로 이미 고쳐 둔다("이미 해결됨" 시험용).
  - **과거 티켓 시드**: 중복 시나리오와 "이미 해결됨" 근거용.
  - **자연스러운 결함**: `// BUG` 같은 표시 없이 실제로 있을 법한 결함. 티 나면 AI가 레포만 보고 맞혀 시험이 되지 않는다.
- 시연용 **가상 팀원**과 그룹(예: 프론트, 서버, 외주개발사)을 둔다.
- 도메인 지식은 형준이 직접 입력한다. Workwrap의 정책(삭제 요약 30일 보존, 기능 이름 변경, 요약 생성 정책)도 정상 동작 시나리오 소재로 쓴다.
- [Claude 결정] 시연에서 가상 팀원은 실제 계정으로 존재하고, 형준이 **계정을 전환하며** 가져가기, 이관, 처리 완료, 확인을 직접 수행한다. 자동 시뮬레이션은 하지 않는다.

### 6.11 인증과 권한
- 요청자, 리드, 개발자 세 역할의 권한이 구분되어야 한다. 로그인과 권한은 Better Auth 조직 플러그인으로 구현한다(4.1). 로그인 수단(이메일/비밀번호 등)은 [빌더 재량]이되, 시연 계정 전환이 쉬워야 한다.
- **티켓 열람 범위** [결정]: 프로젝트 멤버(요청자 포함)는 그 프로젝트의 **다른 티켓 원본을 모두 열람**할 수 있다. 따라서 AI 검토 응답은 참조한 티켓을 링크로 보여준다. 프로젝트 멤버가 아닌 사람은 아무것도 볼 수 없다.
- **설정 화면** [결정]: 관리자 화면의 "설정"에서 멤버 목록, 초대, 역할 부여·변경, 내보내기를 한다. [제안] 같은 곳에 **그룹과 그룹원**, 프로젝트 기본 강조색을 둔다.
- [제안] 개인 설정은 별도 화면 없이 상단 프로필 메뉴에서 강조색과 테마만 바꾼다(디자인 규칙 3.1).
- [Claude 결정] 초대 링크로 들어온 사람이 가입하고 프로젝트에 합류하는 **초대 수락 화면**을 둔다.
- [Claude 결정] 내 프로젝트 목록에서 이름과 레포 URL로 **새 프로젝트를 만드는 화면**을 둔다. 만든 사람이 리드가 된다.
- [Claude 결정] **역할은 프로젝트 단위**로 부여한다. 한 사람이 A 프로젝트에서는 리드, B 프로젝트에서는 개발자일 수 있다. 그룹도 프로젝트 단위다.

### 6.12 AI 제공자 API 키 (프로젝트별, 3차) [결정: 프로젝트별 등록·암호화 / Claude 결정: 세부]
- 1차·2차는 시드로 만든 시연 프로젝트(`isDemo`)만 서버 환경 변수의 키로 AI를 쓴다. 프로젝트별 키 등록은 **3차**에 넣는다. [결정, 12절]
- 리드가 **설정 → AI 탭**에서 프로젝트가 쓸 제공자별 API 키(Claude / ChatGPT / Gemini)를 등록한다. 형준의 개인 키를 모든 사용자에게 쓰지 않기 위해서다.
- 저장: AES-256-GCM으로 암호화해 DB에 저장한다. 암호화 키는 서버 환경 변수(`APP_ENCRYPTION_KEY`)에만 있고, 저장값에 키 버전을 붙여 나중에 암호화 키를 교체할 수 있게 한다.
- 노출: 키는 **서버에서만 복호화**해 AI 호출 직전에 쓴다. 화면에는 끝 4자리만 보인다(`sk-…a1b2`). 다시 보기 기능은 없고, 교체와 삭제만 가능하다. 로그와 오류 메시지, Langfuse 추적에 키가 남지 않게 가린다.
- 저장 시 검증: 등록할 때 해당 제공자에 가장 가벼운 요청을 한 번 보내 유효한지 확인한다. 실패하면 저장하지 않는다.
- 키가 없을 때: AI 단계는 모두 건너뛴다. 요청자는 "이 프로젝트는 AI 검토를 쓸 수 없어요. 바로 제출돼요."를 보고, 티켓은 요청자가 고른 대상(없으면 리드 큐)으로 간다. 리드에게는 설정 화면으로 가는 안내 배너를 보여준다.
- **플랫폼 키로 대신 쓰지 않는다.** 서버 환경 변수의 키는 `isDemo` 프로젝트에서만 쓴다.
- 키 등록·교체·삭제는 프로젝트 감사 이벤트로 기록한다(누가, 언제, 어느 제공자, 끝 4자리).

### 6.13 AI 에이전트 설계 역량을 보여주는 방법 [제안, 12절]
"멀티 에이전트가 돌아간다"가 아니라 **"써서 이만큼 나아졌다(또는 이 경우엔 아니었다)"**를 보여준다.
1. **기준선 → 개선 서사**: 1차는 에이전트 하나(리드 혼자)로 만들고, 2차에서 멀티 에이전트를 붙인 뒤 **같은 평가 세트**(6.10의 정답표)로 정확도·비용·지연을 비교한 표를 낸다.
2. **프롬프트 회귀 테스트**: 지시사항이나 모델을 바꿀 때마다 평가 세트를 CI에서 자동으로 돌려 일치율 변화를 남긴다.
3. **제공자 비교**: Claude / ChatGPT / Gemini를 같은 평가 세트로 비교한 리포트.
4. **판단 기록 재생 화면**: 티켓 하나의 에이전트 판단 트리(`ai_judgments`, `parentJudgmentId`)를 다시 보여주는 읽기 전용 공개 데모.
5. **만드는 과정 기록**: 설계·계획·작업 기록을 레포에 남기고 개인 블로그에 결정과 실패를 연재한다.
6. **MCP 서버**(4차): 티켓 시스템을 MCP로 열어 Claude Code 같은 에이전트가 티켓을 읽고 처리하게 한다.

### 7.1 1차 범위
1차에서 **반드시 잘 동작해야 하는 것**은 다음과 같다. 정해진 날짜는 없다.
1. 등록한 원격 레포(MyProjectManager-sample-repo)에 대한 개요 수준의 이해(6.1)
2. 티켓 작성: 긴급도 고정, 담당 대상(사람/그룹) 지정(6.3, 6.5)
3. 검토 흐름: 중복 확인과 합류, 해소 확인과 분기(철회 / 인터뷰 계속 / 그대로 제출), **에이전트 하나로 하는 인터뷰**, 정리본, 대상 추천(6.3, 인터뷰 설계 10절 1차)
4. 기다리지 않는 검토: 진행 단계 표시와 앱 안 알림(6.3)
5. 배정과 처리: 배정·그룹 큐·리드 큐, 가져가기, 이관, 수락, 보류, 처리 완료, 요청자 확인과 재오픈, 사유별 종결(6.6, 6.7, 6.8)
6. 티켓 상세의 전체 이력 표시와 댓글, 구독, 앱 안 알림 목록(6.7.1)
7. 새 프로젝트 만들기, 초대 수락, 설정(멤버·초대·역할·그룹), 레포 개요 화면(6.1, 6.11)
8. 판단 기록(`ai_judgments`)과 지시사항 버전 저장, 관리자의 도메인 지식·지시사항 편집 화면

## 8. 성공 지표 [제안, 12절에서 변경]
- **중복 등록 방지 수**: 중복 후보에서 "같은 건이에요"를 고른 수
- **AI로 해소된 티켓 비율**: 검토 요청 대비 "철회(AI해소)" 비율, 유형별

- **대상 추천 적중률**: AI 추천 대상과 종결 시점 담당 대상이 같은 비율

- (2차) 평가 세트의 기대 판단 일치율, 에이전트 구성별 비용과 지연

1차에서는 지표 계산에 필요한 상태와 이력을 빠짐없이 기록하고, 대시보드는 3차에 둔다.

## 10. 2차 이후 세부

### 10.1 최종적으로 갖춰야 할 기능 [결정] (3차)
- **다이렉트 메시지(DM)**: 티켓과 별개로, 사용자끼리 1:1 메시지를 실시간으로 주고받는다(웹소켓 같은 실시간 연결). 티켓 안의 댓글(6.7.1)과는 **별도 기능으로 둘 다 존재**한다. [결정]
- **실시간 알림**: 배정, 이관, 처리 완료, 댓글 알림을 실시간으로 전달한다.
- **티켓 처리 현황 지표**: 8절의 지표를 포함한 처리 현황 대시보드.
- 이 세 가지는 장기 목표인 Slack, Jira 대체의 핵심 기능이기도 하다.

### 10.2 1차부터 대비해 둘 것 [Claude 결정]
- 티켓의 모든 상태 변경과 AI 판단을 **이벤트로 기록**한다(이벤트 테이블: 누가/무엇이/언제/이전 값/다음 값). 알림은 이 이벤트를 구독해서 보내고, 지표는 이 이벤트를 집계해서 계산한다. 그러면 나중에 알림과 대시보드를 붙여도 기존 흐름을 고치지 않아도 된다.
- 배포 환경인 Vercel(서버리스)은 웹소켓 연결을 오래 유지하지 못한다. 실시간 기능을 붙일 때는 관리형 실시간 서비스를 쓰거나 별도 실시간 서버를 둔다. 어느 쪽인지는 [빌더 재량]이지만, 1차 코드에서 상태 변경 처리와 알림 전송 사이를 위 이벤트로 분리해 두어 교체가 쉽게 한다.

### 10.3 외부 연동 (4차)
- Slack 알림, Notion 연동, Jira 내보내기 → 장기적으로 대체
- GitHub 외 원격 저장소 지원

### 10.4 보안 모드 로드맵 (4차 이후) [결정: C안]
소스코드가 나가는 곳은 두 군데다: ① 우리 서버(GitHub API로 레포 정보를 읽을 때), ② AI 제공자(개요 분석 시 경로, 설정 파일, README, 커밋 메시지 전달). 이에 대응해 단계적으로 확장한다.
- **로컬 스캔 CLI.** 개발자 PC의 레포 폴더에서 실행해 폴더 구조, 설정 파일, 커밋 이력 같은 사실 정보만 서버로 올린다. 소스 본문은 서버로 가지 않는다.
- **자체 설치형.** 고객사 서버에 Docker 이미지로 설치하고, AI는 고객이 승인한 제공자나 로컬 모델(Ollama 등)을 연결한다. 이 경우 코드가 회사 밖으로 나가지 않는다.
- 데스크톱 설치형(Electron)은 검토 후 제외했다. 협업 도구라 중앙 서버가 어차피 필요하고, 데스크톱 경험은 PWA로 충분하다.
- 지금 미리 해 둘 일은 4.2절의 분리뿐이다.

### 10.5 서비스 가이드 화면 (3차) [결정: 미룸 / 제안: 방식]
- 목적: 요청자가 "원래 이렇게 동작한다"를 스스로 확인해 티켓을 줄이고, 해소 검사가 "정상 동작" 답변의 근거로 가이드를 링크한다.
- 레포만으로는 초안까지만 가능하다(화면 목록, 화면 문구, README, 레포 안의 가이드 페이지). 업무 규칙과 사용 순서는 사람 손이 필요하다.
- 방식: ① AI 초안(레포 재료) ② 도메인 지식으로 보강 ③ 리드 검토 후 게시 ④ "정상 동작"으로 끝난 티켓을 자주 묻는 질문 후보로 수집, 리드 승인 시 추가 ⑤ (더 나중) 실행 중인 서비스 주소로 화면 캡처.
- 게시된 가이드는 해소 검사의 도구로 조회할 수 있게 한다.

## 11. 보류된 사항
