# MyProjectManager 1차(기준선) 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 메인 설계 7.1절과 인터뷰 설계 10절의 1차 범위(리드 에이전트 혼자 하는 AI 검토, 뷔페식 배정, 확인 대기와 사유별 종결, 댓글·구독·앱 안 알림, 레포 개요, 관리자 화면)를 4.1절 기술 스택으로 동작하는 웹앱으로 만든다.

**Architecture:** Next.js App Router 단일 앱. 티켓 생애주기는 순수 함수 상태 기계(`applyAction`)와 낙관적 잠금 서비스(`performAction`)가 맡고, 모든 변경은 같은 트랜잭션에서 `ticket_events`에 기록된다. AI 검토는 하이브리드 구조다. 바깥 단계(중복 확인 → 해소 확인 → 인터뷰 라운드 → 대상 추천 → 정리본)는 `reviewStage`로 고정하고 DB 작업 큐가 한 단계씩 실행하며, 단계 안에서 시스템 에이전트(`runRoleAgent`)가 정해진 도구를 골라 쓰고 zod 스키마로 결과를 낸다. AI 결과는 반드시 정규화 함수(근거 검증)를 거친 뒤에만 요청자에게 보인다. 보안 모드 대비로 `RepoSource`, `getModel`, `BlobStore`를 인터페이스로 분리한다.

**Tech Stack:** pnpm, Next.js 16 (App Router), React 19, TypeScript strict, Neon(Postgres) + Drizzle ORM, Better Auth(조직 플러그인), Vercel AI SDK(`ai`) + `@ai-sdk/anthropic`(기본) + `@ai-sdk/openai` + `@ai-sdk/google`, Langfuse(OpenTelemetry), `@octokit/rest`, Vercel Blob, Tiptap(+ `@tiptap/markdown`, FileHandler, Image), shadcn/ui + Tailwind, TanStack Table, nuqs, cmdk, Motion, sonner, @t3-oss/env-nextjs, react-hook-form + zod, Vitest + `@electric-sql/pglite`, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-24-myprojectmanager-design.md`(메인, PM 리뷰 반영본), `docs/superpowers/specs/2026-11-24-ticket-interview-design.md`(검토·인터뷰), `docs/design/design-rules.md`(화면), `docs/design/diagrams/`(흐름 도식 1~5장)

## Global Constraints

- 레포: `github.com/PorkbellyCode/MyProjectManager`(이 앱). 시연·평가 대상 레포: `github.com/PorkbellyCode/MyProjectManager-sample-repo`(Workwrap 복제 + 결함, 별도 작업으로 준비).
- DB는 Neon 프로젝트 `morning-flower-47053219`의 Postgres만 쓴다(`DATABASE_URL`). 로그인은 Better Auth, 파일은 `BlobStore`(Vercel Blob)로 설계대로 간다. 테스트는 PGlite 인메모리.
- 패키지 매니저는 pnpm만 쓴다. `git stash`를 쓰지 않는다. 화면 문구는 한국어.
- Next.js 16, `ai`, `better-auth`, `@tiptap/*`, Langfuse는 설치된 버전의 문서(`node_modules/next/dist/docs/`, 각 패키지 README)에서 정확한 API 이름을 확인하고 쓴다.
- **AI 원칙(메인 3.1):** AI는 제안만 한다. AI가 티켓의 상태·대상·긴급도·종결을 직접 바꾸는 코드 경로는 없다(시스템 행위자는 `stageReady`, `stageFailed`만 할 수 있다). AI 제안은 근거 검증을 통과해야만 보이고, 근거가 없으면 제안하지 않는다.
- AI는 제출을 막지 않는다. 요청자는 `draft`, `ai_reviewing`, `awaiting_requester` 어디서든 제출할 수 있다.
- 티켓을 바꾸는 모든 쓰기는 같은 트랜잭션에서 `ticket_events` 행을 하나 이상 남긴다. 모든 AI 판단은 `ai_judgments`에 `profileVersionId`, 근거, 토큰 수를 남긴다.
- 프로젝트 멤버가 아닌 사용자의 프로젝트/티켓 접근은 404.
- 긴급도 4단계 `low`, `normal`, `high`, `urgent`. **요청자가 정한 값으로 고정**, 사람만 바꿀 수 있다.
- 확신도 기준값, 부하 기반 자동 배정은 **없다**.
- 질문 라운드 최대 `2`, 라운드당 질문 최대 `3`. `text`·`attachment` 질문은 `justification` 없으면 버린다.
- "안 하기로 함"(`wont_do`) 종결은 리드만. 확인 대기(`resolved`)는 자동 종결하지 않는다.
- 1차 AI는 `projects.isDemo = true`인 프로젝트에서만 서버 환경 변수 키로 실행한다. 그 밖의 프로젝트는 AI 단계를 모두 건너뛰고 "이 프로젝트는 AI 검토를 쓸 수 없어요. 바로 제출돼요."를 보인다. (프로젝트별 키는 3차.)
- 1차 모델 급은 고정: 해소 검사 = 소형, 나머지 = 중형. 모델 ID 형식 `"<provider>:<model>"`, 제공자별 소형/중형 ID는 `lib/ai/models.ts` 한 곳에 둔다(구현 시점 각 제공자 문서의 최신 ID).
- 티켓 본문, 댓글, 도메인 지식, 에이전트 지시사항, 정리본은 마크다운 문자열로 저장한다.
- 파일 업로드는 `BlobStore`, 레포 정보는 `RepoSource`, 모델은 `getModel`만 거친다(`@vercel/blob`, `@octokit/*`, `@ai-sdk/*`를 각 구현 파일 밖에서 import 금지).
- 화면 작업은 `docs/design/design-rules.md`를 따른다. AI 산출물은 ✦ 아이콘 + 제공자 이름 + 연한 바탕으로 표시한다.
- 환경 변수는 `lib/env.ts`로만 읽는다. Langfuse 키가 없으면 추적만 꺼진다.

## Review Focus

1. **검토 단계 중 LLM 실패/시간 초과(60초)/스키마 불일치** → 티켓이 `ai_reviewing`에 갇히지 않고 `awaiting_requester`가 되며 실패 카드 "AI 검토에 실패했어요. 그대로 제출할 수 있어요."가 보인다. (Task 9 테스트)
2. **AI 작업이 도는 중에 요청자가 제출** → 제출이 성공하고, 늦게 끝난 작업 결과는 버려져 상태를 되돌리지 않는다. (Task 9 테스트)
3. **두 개발자가 같은 그룹 큐 티켓을 동시에 가져가기** → 한 명만 성공, 다른 쪽은 충돌 안내. (Task 4 테스트)
4. **AI가 존재하지 않거나 다른 프로젝트의 티켓, 없는 커밋을 근거로 댐** → 그 근거는 제거되고, 남은 근거가 없으면 카드를 띄우지 않는다. (Task 8 테스트)
5. **대상으로 고른 사람이 프로젝트에서 빠졌거나 그룹이 삭제됨** → 제출·지정·이관이 "대상이 이 프로젝트에 없어요"로 거부되고, AI 추천에서는 그 대상이 `null`로 바뀐다. (Task 3, Task 10 테스트)

### Task 3: 티켓 스키마, 담당 대상, 상태 기계

**Files:** Create `lib/db/schema/tickets.ts`, `lib/tickets/targets.ts`, `lib/tickets/state-machine.ts`, `tests/tickets/state-machine.test.ts`, `tests/tickets/targets.test.ts`

**Interfaces:**
- Consumes: `MemberRole`, `groups`, `group_members`, `getMembership`
- Produces:
  - `TicketStatus = 'draft'|'ai_reviewing'|'awaiting_requester'|'withdrawn_ai_resolved'|'queued'|'assigned'|'in_progress'|'on_hold'|'resolved'|'closed'`
  - `Urgency = 'low'|'normal'|'high'|'urgent'`, `Category = 'defect'|'improvement'|'feature'|'inquiry'`
  - `Target = { kind: 'user'; userId: string } | { kind: 'group'; groupId: string } | null` (`null` = 리드 큐)
  - `ReviewStage = 'dedup' | 'resolve' | 'interview' | 'recommend'`
  - `WithdrawKind = 'joined_duplicate' | 'already_resolved' | 'expected_behavior'`
  - `CloseReason = 'resolved_confirmed' | 'wont_do' | 'duplicate' | 'requester_withdrawn' | 'other'`
  - `tickets(id, projectId, number, authorId, title, body(markdown), category, urgency, targetUserId null, targetGroupId null, assigneeId null, status, reviewStage ReviewStage null, interviewRound int default 0, withdrawKind null, closeReason null, closeNote null, duplicateOfId null, aiAvailable boolean, version int default 0, searchVector tsvector generated(title||' '||body, 'simple'), createdAt, updatedAt)`
  - `ticket_events(id, ticketId, actorId null, actorKind 'user'|'ai'|'system', type, from jsonb, to jsonb, reason null, createdAt)`
  - `ticket_attachments(id, ticketId, url, name, size, contentType, createdAt)`
  - `validateTarget(db, projectId, target: Target): Promise<Target>` — 사람은 프로젝트 멤버(요청자 역할 제외)여야, 그룹은 그 프로젝트 것이어야 한다. 아니면 `InvalidTargetError("대상이 이 프로젝트에 없어요")`. `null`은 그대로.
  - `TicketAction` =
    `requestReview` | `stageReady` | `stageFailed` | `continueReview` | `withdraw{kind: WithdrawKind}` | `submit{target: Target}` | `accept` | `claim` | `assignTarget{target: Target}` | `transfer{target: Target; reason}` | `hold{reason}` | `resume` | `resolve{linkedRefs?: string[]}` | `confirmFixed` | `reopen{reason}` | `close{reason: CloseReason; note?; duplicateOfId?}` | `reopenClosed`
  - `ActorCtx = { userId: string | null; role: MemberRole | 'system'; groupIds: string[] }`
  - `applyAction(t: {status; authorId; targetUserId; targetGroupId; assigneeId}, a: TicketAction, actor: ActorCtx): Partial<{status; targetUserId; targetGroupId; assigneeId; withdrawKind; closeReason; closeNote; duplicateOfId}>` — 불가 시 `TransitionError(code: 'invalid_transition'|'forbidden'|'reason_required')`
  - `availableActions(t, actor): TicketAction['type'][]`
  - `placeByTarget(target)` (내부): user → `{status:'assigned', targetUserId, targetGroupId:null, assigneeId:null}`, group → `{status:'queued', targetGroupId, targetUserId:null}`, null → `{status:'queued', both null}`

전이 표(테스트 기준, "그룹원" = `actor.groupIds`에 `targetGroupId` 포함):

| from | action | to | 허용 주체 |
|---|---|---|---|
| draft | requestReview | ai_reviewing | 작성자 |
| ai_reviewing | stageReady / stageFailed | awaiting_requester | system |
| awaiting_requester | continueReview | ai_reviewing | 작성자 |
| awaiting_requester | withdraw | withdrawn_ai_resolved | 작성자 |
| draft, ai_reviewing, awaiting_requester | submit | placeByTarget | 작성자 |
| assigned | accept | in_progress(assignee = 행위자) | 대상 사람 |
| queued(그룹) | claim | in_progress(assignee = 행위자) | 그룹원, lead |
| queued(리드 큐) | claim | in_progress | lead |
| queued(리드 큐) | assignTarget | placeByTarget | lead |
| assigned, queued, in_progress | transfer | placeByTarget(assignee 비움) | 대상 사람·현재 담당자·그룹원(그룹 큐), lead |
| in_progress | hold | on_hold | 담당자 |
| on_hold | resume | in_progress | 담당자 |
| in_progress | resolve | resolved | 담당자 |
