- 작성일: 2026-11-24

## 1. 의도

인터뷰는 두 가지 일을 한다.
1. **해소 시도**: 이미 처리 중, 이미 해결됨, 정상 동작이면 그 자리에서 안내해 티켓을 줄인다.
2. **정보 완성**: 해소되지 않으면, 개발자가 되묻지 않고 바로 일할 수 있도록 빠진 정보를 질문으로 채운다. 결과물은 사람이 읽는 **정리본**(가벼운 PRD)이다.

이 기능은 포트폴리오의 핵심 장면이다. 리드 에이전트가 분야 에이전트를 골라 부르고, 각자의 가설을 합쳐 질문을 만드는 과정이 화면과 기록으로 드러나야 한다.

[결정, 상위 12절] 단계는 **기준선 → 개선** 순서로 간다. 1차는 리드 에이전트 혼자 인터뷰하고(기준선), 2차에서 분야 에이전트를 붙인 뒤 같은 평가 세트로 나아진 정도를 보여준다(상위 6.13).

[결정, 상위 3.1] AI는 **보수적으로** 동작한다. 제안만 하고 값을 바꾸지 않으며, 근거 없으면 제안하지 않고, 모르면 넘어간다.

## 2. 목표, 반목표

### 목표
- 요청자는 대부분 **선택지 클릭만으로** 답한다. [결정]
- 인터뷰 후 개발자가 댓글로 되묻는 일이 줄어든다(측정: 8절).
- 어느 에이전트가 무엇을 근거로 무엇을 제안했는지 전부 기록된다.
- 티켓 난이도에 따라 모델 급과 호출량을 조절해 비용을 아낀다. [결정]

### 반목표
- 제출을 막는 것. 요청자는 언제든 "그대로 제출"할 수 있다. [결정, 상위 문서]
- 티켓 본문에 이미 답이 있는 질문, 앞 라운드에서 한 질문을 다시 묻는 것.
- 한 라운드에 질문 4개 이상, 질문 라운드 3번 이상.
- 정리본이 원문을 대체하는 것. 원문은 항상 보존된다.

## 3. 흐름

```
[작성] ─ AI 검토 요청 ─▶ ① 중복 확인 ──후보 있음──▶ 중복 카드 (같은 건이에요 / 다른 건이에요)
                              │ 없음 또는 "다른 건이에요"          └─ 같은 건 → 작성 내용을 기존 티켓 댓글로 붙이고 구독, 철회(AI해소: 중복 합류)
                              ▼
                         ② 해소 확인 ──근거 있는 제안──▶ 해소 카드 (해결됐어요 / 인터뷰 계속 / 그대로 제출)
                              │ 제안 없음 또는 "인터뷰 계속"
                              ▼
                         ③ 난이도 판정 (2차부터. 1차는 고정 급)
                              ▼
                         ④ 질문 라운드 (최대 2라운드, 라운드당 질문 ≤3)
                            1차: 리드 혼자 질문 작성
                            2차: 리드 → 분야 에이전트 선택(급별 상한) → 병렬 가설·질문 → 리드가 합침
                              ▼ 요청자 답변 (선택지 위주)
                         ⑤ 필요 정보가 다 차거나 2라운드가 끝나면 → 분류가 담당 대상 추천을 미리 채움 → "제출" 버튼 강조
                              ▼ 요청자가 대상을 확인·변경하고 제출
                         ⑥ 정리자가 정리본 작성 → 대상에 따라 배정됨 / 그룹 큐 / 리드 큐 (상위 6.6)
```

- [Claude 결정] "검토 왕복"은 **중복·해소 확인 1회 + 질문 라운드 최대 2회**다.
- [결정] **중복을 먼저 본다.** 비슷한 티켓을 링크로 보여주고 요청자가 고른다. "같은 건이에요"면 작성 내용은 기존 티켓의 댓글이 되고 요청자는 구독자가 된다. "다른 건이에요"면 AI 판단과 달라도 그대로 진행한다. (상위 6.3)
- [결정] 해소 제안("이미 해결됨", "정상 동작")은 **근거가 있을 때만** 띄운다. 자동 철회는 없고, 요청자가 분기 버튼으로 고른다. (상위 3.1, 6.3)
- [결정] **기다리지 않아도 된다.** 검토를 요청한 뒤 화면을 떠나도 되고, 중복 카드·해소 카드·질문이 준비되면 앱 안 알림이 간다. 티켓 화면에는 지금 단계("중복 확인 중 → 해소 확인 중 → 질문 준비 중 → 답변 대기")가 보인다. 1차 갱신은 폴링 또는 SSE다.
- [결정] 요청자가 마지막 질문에 답하고 **제출 버튼을 누르면 바로 제출**된다. 제출 전 정리본 확인 단계는 없다.
- [결정] 정리본은 요청자도 볼 수 있고 고칠 수 있다. [제안] 고칠 수 있는 기간은 **담당자가 수락하거나 가져가기 전까지**. 수정은 이벤트 `summary_edited`로 기록되고 담당자에게 알림이 간다. 이후 보충은 댓글로 한다.
- [Claude 결정] **바로 제출**한 티켓: 요청자에게 말을 걸지 않고 ①② 확인(조용히) → ⑥ 정리본(원문만으로). 중복 후보와 해소 근거, 대상 추천은 **비고로만** 남고, 대상은 요청자가 고른 그대로(없으면 리드 큐) 간다. 정리본에는 "인터뷰 없이 제출됨"과 채움률이 표시된다.
- [Claude 결정] 해소 카드에서 "그대로 제출"을 누르면 인터뷰 없이 ⑤의 대상 확인으로 넘어간다.

## 4. 질문

### 4.1 필요 정보 목록 [제안]
카테고리마다 "이게 채워지면 개발자가 바로 일할 수 있다"는 항목 목록을 둔다. **관리자가 설정에서 고친다**(배포 없이 수정 원칙).

| 카테고리 | 기본 항목 |
|---|---|
| 결함 | 재현 순서 / 기대 결과 / 실제 결과 / 환경(기기·브라우저·앱 버전) / 빈도 / 영향 범위 / 스크린샷 |
| 개선 | 현재 불편 / 원하는 모습 / 누가·얼마나 자주 겪는지 / 지금 쓰는 우회 방법 |
| 신규 기능 | 필요한 이유 / 쓰는 사람 / 성공 기준 / 급한 정도와 이유 |
| 문의 | 질문 내용(대부분 본문으로 충분) |

각 항목은 `{key, label, required: boolean, preferredType}`이다. 필수 항목이 모두 차면 인터뷰를 끝낼 수 있다.

### 4.2 질문 형태 [결정: 선택지 우선 / Claude 결정: 유형]
| 유형 | 화면 | 비고 |
|---|---|---|
| `single` | 버튼 중 하나 | 항상 "직접 입력", "모르겠어요" 포함 |
| `multi` | 여러 개 선택 | 동일 |
| `scale` | 정도(예: 매번/가끔/한 번) | 동일 |
| `text` | 짧은 글 입력 | 선택지를 만들 수 없을 때만 |
| `attachment` | 스크린샷·파일 첨부(Tiptap 업로드 재사용) | 화면 문제 등 꼭 필요할 때만 |

- 질문 하나 = `{id, fillsKey(필요 정보 항목), type, prompt, options?, why(한 줄 이유), askedBy(에이전트 id들)}`.
- `text`, `attachment` 질문은 `justification`(왜 선택지로 못 묻는지)이 있어야 한다. 없으면 리드가 버린다.
- 선택지는 에이전트가 티켓 내용을 보고 **추측한 답을 앞에** 둔다.
- "모르겠어요"는 그 항목을 "알 수 없음"으로 채운 것으로 본다(다시 묻지 않음).

### 4.3 화면 [Claude 결정]
```
✦ Claude  해소된 건 없어 보여요. 빨리 처리되도록 몇 가지만 물을게요.   라운드 1/2
   ┌ 진행: 리드 → 프론트엔드 ✓  AI 기능 ✓  (분석 완료)
   1. 어디서 겪으셨나요?  · 담당 대상을 정하는 데 필요해요
      [모바일 앱] [PC 웹] [둘 다] [직접 입력] [모르겠어요]
   2. 매번 그런가요?
      [매번] [가끔] [한 번만] [모르겠어요]
   3. 문제가 보이는 화면을 캡처해 주실 수 있나요?  · 화면 문제라 글로는 설명이 어려워요
      [이미지 붙여넣기 또는 끌어다 놓기]
                                   [그대로 제출]  [답변 보내기]
```
- 질문을 만드는 동안 진행 상황(어느 에이전트를 불렀고 끝났는지)을 1.5초 간격으로 갱신해 보여준다(실시간 연결 없이 새로고침 방식). 1차는 리드 한 줄만 보인다.
- 마지막 라운드 답변 뒤에는 "답변 보내기" 대신 **"제출"** 버튼이 강조된다.

## 5. 에이전트

### 5.1 종류 [결정: 관리자가 추가·삭제·역할 부여 / 제안: 구분]
| 종류 | 구성 | 관리자 권한 |
|---|---|---|
| 시스템 | **리드**(질문 작성. 2차부터 난이도 판정, 분야 에이전트 선택, 질문 합치기), **해소 검사**(중복 확인과 해소 확인), **정리자**, **분류**(담당 대상 추천), **범용**(2차, 맞는 분야가 없을 때) | 지시사항·모델 수정. 삭제·추가 불가 |
| 분야 (2차) | 예: 프론트엔드, 서버, AI 기능, 보안, QA 관점 | **추가, 삭제, 켜기/끄기, 역할 부여**, 지시사항·모델 수정 |

- **역할 부여 = 담당 범위 지정** [결정]: 분야 에이전트의 `scopeDescription`(리드가 읽고 고를 때 쓰는 설명)과 선택적 `groupId`(연결된 그룹, 상위 6.6)를 정한다. 권한(중복 판정, 대상 추천 등)은 에이전트별로 열지 않고 시스템 에이전트에 고정한다. [제안, 형준 동의]
- 분야 에이전트에게 넘기는 자료는 **자기 범위로 한정**한다. 그룹이 연결돼 있으면 그 그룹 태그가 붙은 레포 개요, 그 그룹의 최근 티켓, 관련 도메인 지식만. 그룹이 없는 관점 에이전트는 티켓 본문과 도메인 지식 전체.
- [제안] 2차부터, 그룹마다 분야 에이전트를 하나씩 만들되 **꺼진 상태**로 둔다. 켤지는 아래 추천과 관리자가 정한다.
- **리드 혼자 모드** [제안]: 설정 스위치. 켜면 리드가 분야 에이전트 없이 혼자 질문을 만든다. 1차의 유일한 동작 방식(기준선)이고, 2차부터는 소규모 추천 구성이자 평가에서 "에이전트 하나 vs 리드+분야"를 비교하는 데 쓴다.

### 5.2 추천 구성 (3차) [결정: 기능 / 제안: 판단 방식]
에이전트 관리 화면의 **"추천 구성 보기"**.
- 입력: 최신 레포 스냅샷(파일 수, 모듈 수, 화면·API 수, 기술 스택 수, `truncated` 여부), 그룹 수, 멤버 수, 최근 30일 커밋·PR 수, 최근 30일 티켓 수.
- 규모 판정은 **규칙 점수**로 한다(AI 아님, 같은 입력이면 같은 결과). [Claude 결정]
  - 소규모: 리드 혼자 모드 + 범용
  - 중규모: 그룹별 분야 에이전트 켜기
  - 대규모: 그룹별 + 관점 에이전트(보안, QA, 성능) 추가 제안
- 점수 구간과 가중치는 [빌더 재량]이되, MyProjectManager-sample-repo(Workwrap 기반, 파일 약 120개, 그룹 3개)는 **소규모**로 나와야 한다.
- 결과 화면: 추천 구성, 항목별 근거 한 줄, 현재 구성과의 차이. **"적용"을 눌러야 반영**된다.
- 시연: 테스트 레포는 소규모 추천을 보여준 뒤, 관리자가 분야 에이전트를 직접 켜는 장면으로 진행한다.

### 5.3 오케스트레이션 (2차) [결정: 리드+분야 / 제안: 세부]
1. 리드가 티켓(원문, 지금까지의 답변, 필요 정보 목록의 빈칸)을 보고 켜진 분야 에이전트 중 **급별 상한 이내**로 고른다. 고른 이유를 남긴다. 맞는 분야가 없으면 범용을 부른다.
2. 고른 에이전트들을 **병렬 실행**한다. 각자 출력: `{hypotheses: [{text, confidence}], groupFit: {groupId, note} | null, proposedQuestions: Question[], evidence: [{ref, note}]}`.
3. 리드가 합친다: 같은 항목을 채우는 질문은 하나로, 본문·이전 답변으로 이미 채워진 항목은 제외, 우선순위(필수 → 영향 큼) 순으로 3개까지.
4. 분야 에이전트 하나가 실패하거나 시간 초과(30초)면 나머지로 진행한다. 전부 실패하면 리드 혼자 모드로 다시 시도하고, 그것도 실패하면 "AI 질문을 만들지 못했어요. 그대로 제출할 수 있어요."
5. 모든 호출은 `ai_judgments`에 남기고, 분야 에이전트 판단은 리드 판단의 하위(`parentJudgmentId`)로 묶는다.

### 5.4 담당 대상 추천 [결정: 추천만 / 제안: 근거]
- 분류 에이전트는 ⑤에서 **추천 대상 하나**(사람 또는 그룹)와 근거를 낸다. 근거: 그룹의 담당 범위 설명과 레포 태그, 비슷한 과거 티켓의 종결 시점 담당 대상, (2차) 분야 에이전트의 `groupFit`.
- **판단이 어려우면 추천하지 않는다.** 확신도 기준값은 두지 않는다. 추천이 없으면 요청자가 고른 대상, 그것도 없으면 리드 큐로 간다. (상위 3.1, 6.6)
- 추천은 미리 채워질 뿐이고, 요청자가 확인하거나 바꿔야 제출된다. 바뀌면 원래 추천과 최종 선택이 이력에 남는다(추천 적중률 지표).

## 6. 모델 급 조절 (2차) [결정]

1차는 모든 역할을 **고정 급**(중형, 해소 검사만 소형)으로 돌린다. 이 절은 2차부터다.

- 리드가 ②에서 가장 싼 모델로 티켓 난이도를 **가벼움 / 보통 / 깊음**으로 판정하고 이유를 남긴다.
  - 가벼움: 단순 문의, 짧은 개선 요청
  - 보통: 대부분의 결함·개선
  - 깊음: 긴급 결함, 여러 그룹에 걸친 문제, 원인이 모호한 결함
- 급별 자원 [Claude 결정, 관리자가 수정 가능]:

| 급 | 모델 급 | 분야 에이전트 상한 | 도구 호출 상한 |
|---|---|---|---|
| 가벼움 | 소형(Claude: Haiku급) | 1 | 3 |
| 보통 | 중형(Sonnet급) | 2 | 6 |
| 깊음 | 대형(Opus급) | 3 | 10 |

- 급별 모델은 **제공자별 매핑표**로 관리자가 지정한다(Claude / ChatGPT / Gemini 각각 소·중·대). 에이전트 프로필의 모델 지정이 있으면 그것이 우선한다.
- 긴급도가 `urgent`이면 최소 보통 급. [Claude 결정]
- [Claude 결정] (3차) **다른 급으로 다시 실행**은 리드 사용자가 **제출된 티켓**에서만 할 수 있다. 요청자가 인터뷰 중인 티켓에는 끼어들지 않는다. 재실행은 해소 확인·정리본·대상 추천을 새 급으로 다시 만들어 **기존 결과 옆에 비교용으로** 보여준다. 리드가 "이 결과 적용"을 눌러야 반영되며, 요청자가 정리본을 이미 고쳤다면 정리본은 덮어쓰지 않고 대상 추천만 참고로 보여준다(대상은 사람이 바꾼다). 모든 재실행은 기록된다.
- [Claude 결정] **분야 에이전트도 도구를 쓴다.** 도구는 그 에이전트의 범위로 걸러진 결과만 돌려준다(그룹이 연결된 에이전트는 `searchTickets`, `getRepoOverview`, `listRecentChanges`가 그 그룹으로 필터링됨). 표의 도구 호출 상한은 **에이전트 한 개당** 값이다. 리드 자신은 도구를 쓰지 않고 분야 에이전트의 결과만 합친다.
- [Claude 결정] **어느 제공자의 매핑을 쓸지**: 프로젝트 설정에 **"기본 AI 제공자"**(Claude / ChatGPT / Gemini)를 새로 둔다. 급별 모델은 이 제공자의 열에서 고르고, 디자인 규칙의 프로젝트 기본 강조색도 이 설정을 따른다(디자인 규칙 3.1의 "검토 에이전트 제공자 기준"을 대체). 개별 에이전트에 다른 모델을 지정하면 그 에이전트만 예외다. 1차부터 Gemini 제공자(`@ai-sdk/google`)를 레지스트리에 넣는다.
- 비용 표시: 판단마다 입력·출력 토큰과 추정 비용을 저장해, 관리자 화면에서 "티켓당 평균 비용"을 보여줄 수 있게 한다(화면은 2차, 데이터는 1차부터).

## 7. 정리본 [결정: 요청자 열람·수정 / 제안: 형식]
- 정리자가 제출 시점에 작성한다. 형식: `{summary, fields: {[key]: value | '알 수 없음' | null}, fillRate: 채운 필수 항목/전체 필수 항목, attachments, generatedFrom: 'interview'|'original_only'}`.
- 티켓 상세 맨 위에 정리본, 그 아래 원문, 그 아래 인터뷰 전체 기록(질문·답변·각 에이전트의 가설과 근거).
- 정리본은 마크다운으로도 저장해 검색·검토 에이전트가 읽을 수 있게 한다.

## 8. 성공 지표 [제안]
- 인터뷰를 거친 티켓의 평균 채움률
- 배정 후 개발자의 "되묻기" 댓글 수(인터뷰 거친 티켓 vs 바로 제출한 티켓)
- 질문 라운드당 평균 소요 시간, 티켓당 평균 비용
- 중복 후보에서 "같은 건이에요" 비율, 해소 제안 수락률과 **철회 후 재등록 비율**(잘못된 해소 제안 감시)
- 2차: 같은 평가 세트(상위 6.10 정답표)로 "리드 혼자" vs "리드+분야" 비교: 기대 판단 일치율, 비용, 지연

## 9. 상위 문서와 달라지는 점
- 상위 6.3의 요청자 흐름(중복 확인 → 해소 확인 → 인터뷰 → 대상 추천)과 이 문서 3절은 같은 흐름을 다른 깊이로 적은 것이다.
- 6.9의 "검토 에이전트"는 해소 검사 에이전트가 되고, 리드·분야·정리자·범용 에이전트가 추가된다.
- 상위 6.11 설정 화면에 **에이전트 탭**이 추가된다. 1차는 시스템 에이전트 지시사항 편집만, 2차에 분야 에이전트 관리·리드 혼자 모드·급별 모델 매핑·필요 정보 목록, 3차에 추천 구성.
- [결정, 상위 12절] 이전 설계의 "영역"과 확신도 기준값, 부하 기반 자동 배정, AI의 긴급도 조정은 없어졌다.

## 10. 단계별 범위 [결정: 단계 분할, 상위 7절]
- **1차 (기준선)**: 3절 흐름 전체를 **리드 혼자**로(중복 확인과 합류, 근거 있는 해소 제안과 분기, 질문 라운드, 대상 추천, 정리본과 요청자 수정), 진행 단계 표시와 앱 안 알림, 시스템 에이전트 지시사항 편집, 기본 AI 제공자 설정(시연 프로젝트는 서버 키), 판단 기록과 토큰·비용 저장.
- **2차 (개선 증명)**: 분야 에이전트와 오케스트레이션(5.3), 분야 에이전트 추가·삭제·켜기/끄기·역할 부여, 난이도 판정과 급별 모델 조절(6절), 급별 모델 매핑·필요 정보 목록 편집 화면, 평가 세트 실행과 비교 리포트, 티켓당 비용 화면.
- **3차**: 프로젝트별 AI 키(상위 6.12), 추천 구성 보기(5.2), 다른 급으로 다시 실행.
